# Flow Monitor Agent - Concept Document

**Created:** 2025-12-30
**Updated:** 2025-12-30
**Status:** Draft - Design Phase
**Purpose:** AI agent that analyzes Flow Monitor alerts and makes trading recommendations

---

## Mission Statement

The Flow Monitor Agent uses data gathered by the Option Scanner's multiple strategy modules to analyze alerts, track institutional flow, and recommend when to enter positions. Its job is to decide how to act on alerts generated by Flow Monitor, creating actionable intelligence from raw flow detection.

**Cross-Strategy Intelligence:** While triggered by Flow Monitor alerts, the agent leverages data from Option Pipeline (OI trends), News Collector (context), Earnings Intel (events), and market data to make holistic recommendations.

---

## Core Functionality

### Primary Objective
Create and maintain **dossiers** (ongoing narratives) for option contracts that receive alerts. Each dossier tracks:
- Contract identification and initial alert context
- Institutional flow analysis (true smart money vs imitators/hedges)
- Historical pattern matching
- Entry/exit recommendations
- Status tracking (active monitoring vs closed)

### Key Principles
1. **One dossier per contract** - Multiple alerts on same contract update existing dossier, don't create new ones
2. **Big picture analysis** - Uses data from Flow Monitor, Option Pipeline, market data, earnings intel, etc.
3. **Confidence-based recommendations** - Only recommends positions when confident; it's okay to find nothing actionable
4. **Dossier lifecycle** - Opens on alert, updates as new data comes in, closes when no longer worth following
5. **Permanent record** - All analysis stored in `datalake.db`, automatically synced to `datalake_query.db`

## System Architecture

### Module Structure

**Core Infrastructure Pattern:**
```
agents/                          # Core agentic framework (like core/ for AI infrastructure)
├── agent_runtime.py            # Anthropic SDK, tool use loop, orchestration
├── agent_tools.py              # Shared tools: query_database, send_email, update_dossier
├── agent_prompts.py            # Base prompt templates
├── agent_logger.py             # Console/file logging system
├── agent_memory.py             # Memory system (Phase 2)
└── agent_config.py             # Agent-specific configuration

strategies/flow_monitor/
├── fm_agent.py                 # FM-specific wrapper:
│                               # - FM-specific prompts
│                               # - Dossier logic
│                               # - Calls agents/agent_runtime.py with FM context
└── fm_main.py                  # Orchestrates: scan → alerts → agent
```

**Design Rationale:**
- Matches existing pattern: `core/` provides shared infrastructure, strategies use it
- `agents/` is fundamental system infrastructure (like `core/tradier_api.py`)
- FM-specific wrapper (`fm_agent.py`) contains Flow Monitor context
- Future: `op_agent.py`, `ei_agent.py` can reuse same runtime/tools/logging
- Scalable: New agent types share core framework

### Database Architecture

**Production Database: `data/datalake.db`**
- Agent **writes** to this database (new tables: `flow_contract_dossiers`, `flow_dossier_updates`, `agent_actions`)
- WAL mode enabled (same as Flow Monitor)
- 30-second busy timeout for lock handling
- Tables automatically synced to query database

**Query Database: `data/datalake_query.db`**
- Agent **reads** from this database when possible (analysis, cross-strategy queries)
- Updated via two sync mechanisms:
  - **Full sync:** 3x daily (7:20 AM, 5:45 PM, 7:00 PM) - copies entire database
  - **Quick sync:** After each FM scan cycle (~20 min) - copies specific tables only
- Agent tables included in both sync types (see modifications below)

**Concurrency Safety:**
- Flow Monitor writes to: `flow_options_scans`, `flow_alerts`, `flow_symbol_summary`
- Agent writes to: `flow_contract_dossiers`, `flow_dossier_updates`, `agent_actions`
- **No table overlap** = minimal write conflicts
- WAL mode allows concurrent writes to different tables
- Busy timeout (30s) handles brief conflicts during WAL checkpoints

**Sync Behavior:**
- **Full sync** copies entire database (including new agent tables) - no modification needed
- **Quick sync** requires modification to include agent tables:
  ```python
  # In db_backup.py line 686, update tables_to_sync:
  tables_to_sync = [
      'flow_alerts',
      'flow_options_scans',
      'flow_contract_dossiers',      # ADD
      'flow_dossier_updates',        # ADD
      'agent_actions'                # ADD
  ]
  ```
- **Rationale:** Agent dossiers should be visible in query DB during market hours for user analysis
- Without quick sync: Agent data stale until next full sync (could be hours)

### Email Integration

**Uses existing email infrastructure:**
- Configuration: `config.json` → `notifications.email`
- Same pattern as `tools/market_report_emailer.py`
- SMTP settings, recipients, enabled flag already configured

### Contract Identification

**Uses existing universal contract hash:**
- Format: `SYMBOL|STRIKE|EXPIRATION|TYPE`
- Example: `NVDA|500.0|2025-12-19|CALL`
- Generated by: `generate_contract_hash()` (used in FM and OP collectors)
- Primary key across all option-related tables

### Orchestration

**Flow Monitor Integration:**
```python
# In fm_main.py after scan cycle completes:
from strategies.flow_monitor.fm_agent import FMAgent

# After alerts are stored
if alerts_generated:
    agent = FMAgent()
    agent.analyze_new_alerts(scan_timestamp)  # Non-blocking, runs async
```

**Execution Flow:**
```
FM Scan (20 min) → Store Scans → Generate Alerts → Sync Query DB → Launch Agent → Next Scan
                                                                          ↓
                                                              Agent has ~20 min to work
                                                              Reads from query DB
                                                              Writes to primary DB
```

**Agent Benefits from 20-Minute Window:**
- Can run multiple Claude API calls per alert
- Build rich narratives
- Query multiple strategy tables
- No rush - next scan won't start until ~20 min later

## Agent Modes

### Mode 1: Post-Alert Review (MVP - Build This First)
**Trigger:** After each Flow Monitor scan cycle
**Runtime:** ~20 minutes (between scans)

**Process:**
1. Load new alerts from latest scan
2. For each alert:
   - Check if dossier exists for this contract
   - If yes: update existing dossier with new information
   - If no: create new dossier
3. Query relevant context (OI data, historical patterns, market conditions)
4. Analyze flow characteristics (institutional vs day trading vs hedging)
5. Update dossier with findings
6. Determine if immediate action warranted → send email if yes
7. Mark dossier status (active monitoring / closed / urgent)

**Output:**
- Updated dossier in database
- Optional email if urgent/actionable
- Console log of agent reasoning

### Mode 2: Contract Monitoring (Phase 2)
**Trigger:** Mid-day check (between scan cycles)
**Purpose:** Track contracts with open dossiers for entry/exit signals

**Process:**
1. Load all active dossiers
2. Check for changes (price drops, new flow, outflow detection)
3. Update recommendations
4. Send email if entry opportunity or exit signal

### Mode 3: Daily Synthesis (Phase 2)
**Trigger:** End of trading day
**Purpose:** Reflect, learn, summarize

**Process:**
1. Review all dossiers from today
2. Identify patterns and lessons
3. Update agent memory
4. Send daily summary email (always sent)

## Database Schema

### New Tables

#### `flow_contract_dossiers`
**Purpose:** One record per contract being tracked (the "dossier")

```sql
CREATE TABLE flow_contract_dossiers (
    dossier_id INTEGER PRIMARY KEY AUTOINCREMENT,

    -- Contract identification
    contract_hash TEXT NOT NULL,           -- Unique contract identifier
    symbol TEXT NOT NULL,
    strike REAL NOT NULL,
    expiration TEXT NOT NULL,
    option_type TEXT NOT NULL,             -- 'call' or 'put'

    -- Dossier lifecycle
    created_at TEXT NOT NULL,              -- First alert timestamp
    updated_at TEXT NOT NULL,              -- Last update timestamp
    status TEXT NOT NULL,                  -- 'active', 'monitoring', 'closed', 'urgent'
    close_reason TEXT,                     -- Why dossier was closed

    -- Current narrative
    narrative TEXT,                        -- Agent's full story/analysis
    flow_classification TEXT,              -- 'institutional', 'day_trading', 'hedging', 'unknown'
    confidence_level REAL,                 -- 0.0-1.0 agent confidence

    -- Recommendation
    current_recommendation TEXT,           -- 'enter_now', 'monitor', 'wait_for_entry', 'exit', 'pass'
    recommendation_reasoning TEXT,         -- Why this recommendation
    entry_target_price REAL,               -- Price agent thinks is good entry

    -- Tracking
    alert_count INTEGER DEFAULT 1,         -- How many alerts triggered on this contract
    last_alert_id INTEGER,                 -- FK to flow_alerts

    UNIQUE(contract_hash)
);

CREATE INDEX idx_dossiers_status ON flow_contract_dossiers(status);
CREATE INDEX idx_dossiers_symbol ON flow_contract_dossiers(symbol);
CREATE INDEX idx_dossiers_updated ON flow_contract_dossiers(updated_at);
```

#### `flow_dossier_updates`
**Purpose:** Audit trail of every time agent updates a dossier

```sql
CREATE TABLE flow_dossier_updates (
    update_id INTEGER PRIMARY KEY AUTOINCREMENT,
    dossier_id INTEGER NOT NULL,
    alert_id INTEGER,                      -- Which alert triggered this update (if any)
    update_timestamp TEXT NOT NULL,

    -- What changed
    previous_status TEXT,
    new_status TEXT,
    previous_recommendation TEXT,
    new_recommendation TEXT,

    -- Agent's reasoning
    update_narrative TEXT,                 -- What agent learned/decided in this update
    queries_executed TEXT,                 -- JSON: list of SQL queries agent ran
    context_gathered TEXT,                 -- JSON: key data points agent used

    -- Action taken
    email_sent BOOLEAN DEFAULT FALSE,
    email_type TEXT,                       -- 'immediate_action', 'entry_opportunity', 'exit_signal'

    FOREIGN KEY (dossier_id) REFERENCES flow_contract_dossiers(dossier_id),
    FOREIGN KEY (alert_id) REFERENCES flow_alerts(id)
);

CREATE INDEX idx_updates_dossier ON flow_dossier_updates(dossier_id);
CREATE INDEX idx_updates_timestamp ON flow_dossier_updates(update_timestamp);
```

#### `agent_actions`
**Purpose:** Record of all actions agent took (emails, dossier operations, etc.)

```sql
CREATE TABLE agent_actions (
    action_id INTEGER PRIMARY KEY AUTOINCREMENT,
    action_timestamp TEXT NOT NULL,
    action_type TEXT NOT NULL,             -- 'email_sent', 'dossier_created', 'dossier_updated', 'dossier_closed'

    dossier_id INTEGER,                    -- Related dossier (if applicable)
    alert_id INTEGER,                      -- Related alert (if applicable)

    action_details TEXT,                   -- JSON: specific details
    reasoning TEXT,                        -- Why agent took this action

    -- User feedback (populated later)
    user_feedback TEXT,                    -- User's response/override
    outcome TEXT,                          -- What actually happened

    FOREIGN KEY (dossier_id) REFERENCES flow_contract_dossiers(dossier_id),
    FOREIGN KEY (alert_id) REFERENCES flow_alerts(id)
);

CREATE INDEX idx_actions_timestamp ON agent_actions(action_timestamp);
CREATE INDEX idx_actions_type ON agent_actions(action_type);
```

#### `agent_memory` (Phase 2 - Learning System)
**Purpose:** Agent's learned patterns and lessons

```sql
CREATE TABLE agent_memory (
    memory_id INTEGER PRIMARY KEY AUTOINCREMENT,
    memory_type TEXT NOT NULL,             -- 'pattern', 'lesson', 'heuristic'
    created_date TEXT NOT NULL,

    title TEXT NOT NULL,                   -- Short description
    description TEXT,                      -- Full explanation

    evidence TEXT,                         -- JSON: supporting data points
    confidence REAL,                       -- How confident is agent (0.0-1.0)

    times_applied INTEGER DEFAULT 0,       -- Usage tracking
    success_rate REAL,                     -- Accuracy when applied

    last_reviewed TEXT,
    should_retire BOOLEAN DEFAULT FALSE,   -- Agent flags for deprecation

    metadata TEXT                          -- JSON: flexible storage
);
```

### Changes to Existing Tables

**No changes needed to `flow_alerts`** - it remains the raw alert detection table.

**Relationship:**
- `flow_alerts` = raw detection events (many alerts can fire for same contract)
- `flow_contract_dossiers` = one ongoing story per contract
- `flow_dossier_updates` = history of how that story evolved
- `agent_actions` = what the agent did about it

## Email Communication

### Style Guide
- **Plain language:** "dropped 75%" not "collapsed"
- **Get to the point:** First sentence explains what happened
- **Avoid jargon:** Unless necessary
- **No weasel words:** "might", "could", "possibly"
- **Actionable:** Tell user what to do, if anything
- **Reference work:** Link to dossier for full analysis

### Email Types

#### 1. Immediate Action
**Sent:** Rarely - only when something urgent is happening RIGHT NOW
**Example subject:** "Flow Alert: NVDA $500 Calls - Institutional Buying NOW"

#### 2. Entry Opportunity
**Sent:** When a monitored contract becomes attractive to enter
**Example subject:** "Entry Opportunity: NVDA $500 Calls Down 75%"

Template:
```
Remember the alert from Monday at 10:45 AM for NVDA $500 Dec 19 calls?
The contract dropped 75% today to $1.60.

I think the original thesis still holds. The open interest increased by
8,200 contracts yesterday, confirming institutional positioning. The stock
only needs to reach $502 by Dec 19 for these to be profitable.

If you buy at $1.60, even a return to Monday's price of $6.50 would give
you a 306% gain. I think this dip is noise, not a change in the underlying
pattern.

This opportunity probably won't last more than a day or two based on
historical patterns.

See my work: [dossier link]
```

#### 3. Exit Signal
**Sent:** When a position should be exited
**Example subject:** "Exit Signal: TSLA $250 Puts - Major Outflow Detected"

#### 4. Daily Summary
**Sent:** Every trading day (Phase 2)
**Example subject:** "Daily Summary - Dec 30, 2025"

## Agent Decision Framework

### Identifying True Institutional Flow

**Characteristics the agent looks for:**
- Volume-to-OI ratio >15:1 (new position opening)
- Multiple waves of volume (accumulation pattern)
- Minimal OI yesterday (not rolling existing positions)
- Size relative to typical symbol volume
- Timing patterns (morning vs afternoon)
- Coordination with stock movement

**Red flags for imitators/hedges:**
- Volume matches but OI doesn't increase next day
- Opposite side also shows high volume
- Coincides with news/earnings (reactive, not predictive)
- Spread patterns (buying calls AND puts)

### Dossier Status Transitions

```
New Alert → Create Dossier (status: 'active')
    ↓
Analyze Flow → Update (status: 'monitoring' or 'urgent')
    ↓
Entry Signal → Email + Update (status: 'active')
    ↓
No Longer Interesting → Close (status: 'closed', reason: documented)
    ↓
New Alert on Same Contract → Reopen (status: 'active')
```

### Closure Heuristics

Agent may close a dossier when:
- OI didn't confirm (day trading pattern detected)
- Contract expired
- Thesis invalidated (opposite flow detected)
- Time decay makes position unattractive
- Better opportunities identified
- User feedback indicates not interested
